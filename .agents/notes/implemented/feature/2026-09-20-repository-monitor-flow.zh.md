# Agent Note: 仓库监视流程图

Status: implemented

[English](2026-09-20-repository-monitor-flow.md) | 中文

## 问题

仓库标签页已经展示有大小上限的 Git 检查点，但没有提供添加仓库目标的入口，也没有说明变更如何从工作区快照流转到可见更新。

## 决策

保持本地工作区证据只读且归会话所有。新增浏览器本地目标存储、监视开关、从仓库到状态读取、变更解析、监视更新的四阶段流程，以及面向公开 GitHub URL 的有界提交时间线。公开 GitHub 轮询无需凭据；本地路径和远端地址通过现有 `agent/git-checkpoint` 事件解析，也支持会话工作区下直接嵌套的单个仓库。

## Alternatives considered

**将目标持久化到 Host 或 Session 数据**：不采用，因为仓库路径和 URL 在缺少明确持久化契约前应保持浏览器本地存储，现有 Git 证据也明确归会话所有。

**为每个本地工作区运行后台监视器**：不采用，因为客户端不拥有可靠的跨平台文件监视生命周期；当前检查点事件流是本地变更证据的既有来源。

**立即支持需要鉴权的仓库和非 GitHub 提供商**：不采用，因为凭据存储和各提供商 API 契约会让功能超出手动监视流程的范围。非 GitHub URL 仍可在本地检查点上报相同 `origin` 时变为已连接；暂不支持远端轮询。

## 结果

仓库目标可以在浏览器刷新后保留，但不会发送给宿主或写入 Session 数据。GitHub 轮询只使用公开 HTTPS API 响应并限制提交数量；私有和非 GitHub 目标使用本地检查点元数据，不进行远端轮询。会话工作区下只有一个直接嵌套的 Git 仓库时，会解析到该仓库根目录。监视操作不会写入仓库。

## 验证

仓库地址解析、流程交互、Git 投影、生命周期和包构建的聚焦检查通过。仓库级 GUI 套件仍有与本功能无关的 canvas 和 renderer fixture 既有失败。
