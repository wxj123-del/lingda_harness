# Agent Note：长任务验收——证据复验、自动续跑与机制基准

状态：已实现

[English](2026-10-20-long-task-acceptance.md) | 中文

## 问题

第一轮长任务改造让任务持久化、以证据把关完成、并约束单轮预算。仍有三个缺口。

证据只能证明某条命令在更早的某个时刻通过过，无法证明它现在仍然通过。若在记录之后引入回归，任务仍能凭过期证据完成。

并非模型主动决定的停止——预算上限或崩溃——会终结工作。会话修复路径只关闭中断的轮次就停下，下一步要等人推动。

没有任何东西度量这些机制是否真的端到端生效。既有基准都只测延迟与内存，而不是「闸门拒了没有、续跑发生了没有、会话最终完成了没有」。

## 决策

**证据复验。** `dsh-task-state` 新增 `reverifyEvidence`（默认关闭，基础组合包打开）、`reverifyTimeoutMs` 与 `maxReverifyCommands`。标记任务 `succeeded` 现在分三段执行：先做一次试算，校验覆盖情况并列出支撑任务的不同命令；然后逐条通过 `ctx.tools.execute` 重跑；最后对重新读取的快照再次应用补丁。之所以需要第三段，是因为重跑本身会产生 `tool/result`，被 shell 观察者记为新的自动证据——用重跑前的快照写入会把这份证据丢掉。重跑以嵌套调用身份继承调用方的执行身份，因此 PTC 模式部署不会拒绝原生工具名，审批、沙箱与超时策略也和最初那次完全一致。`reverifyEvidence` 与 `requireVerifiedEvidence: false` 同时出现会在加载时被拒绝：第二段只有在第一段开启时才有意义。

**自动续跑。** `dsh-auto-resume` 读取持久的停止原因，而不是去推断：一条 `budget/stop` 事件，或尾部被标记为 `interrupted`。只有当任务活动且带交接说明、agent 空闲且没有待处理输入、没有 armed goal 负责续跑、尝试次数与冷却都允许时才会续跑。每次续跑先写 `auto-resume/attempt` 再排队提示词，因此两者之间崩溃仍会计入次数。用户取消会把尝试计数设为无穷大，用一项状态就表达了「本会话不再续跑」，而不需要再加一个标志。

**机制基准。** `benchmarks/long-task-acceptance/` 用固定模型驱动三个脚本化场景——被拒的假完成、预算停止后续跑、崩溃后续跑——全部走真实 loop。它只断言 `ok`、`resumes`、`turns`，耗时只记录不评判，因为要回答的是机制是否触发，而不是机器有多快。

## 备选方案

**在新子进程里重跑命令。** 已拒绝：绕过工具管线会跳过审批、沙箱与超时策略，也会让这次执行从会话日志中消失——而这恰恰是复验可信的来源。

**任务活动期间任何轮次结束都续跑。** 已拒绝：模型主动完成的轮次是一种判断，不是中断。继续它会与模型的决定对抗，并诱发循环。

**让 goal 驱动承担全部续跑。** 已拒绝：goal 需要显式启用且受轮数限制；有持久任务但没有 goal 的部署将永远无法续跑。armed goal 守卫避免两者同时驱动。

**用真实模型度量。** 本轮拒绝：真实模型基准度量的是模型能力，不确定，且无法在 CI 运行。机制基准是补充，不是替代。

## 影响

现在，一条曾经通过的命令发生回归，任务会被拒绝完成——这对自认为已经做完的模型是一种新的失败模式，错误信息会写明命令与退出码，使修复可操作。复验在完成时消耗 token 与墙钟，受命令上限与单条超时约束。自动续跑会在无人确认的情况下消耗 token，受尝试次数、冷却、交接说明要求与 armed goal 守卫约束。不需要这些行为的部署可设置 `reverifyEvidence: false` 或 `maxAutoResumes: 0`。

验证：`packages/todo/task-state/tests/reverify.spec.ts` 覆盖回归、复验成功、三段式之间的证据保全、超时、命令上限、关闭路径、非法配置与纯函数选择；`packages/guard/auto-resume/tests/auto-resume.spec.ts` 覆盖预算续跑、取消、交接说明要求的开关、尝试上限、armed goal 守卫与正常完成；`benchmarks/long-task-acceptance` 报告 3/3。
