# Agent Note: 将 Lingda 打包为单个 npm 发行包

Status: implemented

[English](2026-09-16-lingda-npm-distribution.md) | 中文

## 问题

如果只重命名入口包，再依赖 registry 中的 `@deepseek-ai/*` 版本，安装的会是上游代码，而非 Lingda 的定制包。重命名所有工作区包又会改变内部导入和插件标识。

## 决策

[Lingda 打包命令](../../../../scripts/release/lingda.ts) 从 CLI 以及可选媒体、Token trace 插件出发，收集本地运行时依赖和 peer 依赖。它通过 `pnpm pack` 遵循各包的发布文件规则，把这些归档和 SHA-512 校验值放进一个 `lingda-harness` 归档。首次启动时，[运行时安装器](../../../../distribution/npm/runtime.mjs) 校验归档，将其作为显式本地依赖与外部依赖一起安装，再通过原子重命名放置已完成的运行时目录。缓存按归档内容、平台和 Node ABI 隔离。[启动器](../../../../distribution/npm/bin/lingda.mjs) 在同一进程中调用现有 CLI，默认将数据保存在 `~/.lingda`，并遵循 `DSH_HOME` 设置。

[上游发布序列](2026-08-10-npm-release-sequences.zh.md) 对上游包维护仍有独立价值。Lingda 发行包不会向这些包的命名空间发布。

## 考虑过的替代方案

依赖上游 npm 包的别名会丢失本地定制。为所有工作区包发布改名副本，会把改动扩散到导入、插件清单和配置树。在每位用户的电脑上下载并构建源码，会给首次启动增加开发工具要求。没有完整外部依赖的 npm 捆绑依赖会漏装所需外部包。携带本地归档并安装完整依赖树，可以保留插件标识，省去用户侧构建步骤。

## 后果

每次发布都需要完整构建和新的发行包版本。归档体积比轻量启动器大。验证覆盖缺失本地依赖、跨平台依赖选择、干净目录内安装归档以及实际 Web 启动。npm 认证和发布与打包分开。可选原生二进制包沿用上游版本，因此声明支持某个平台之前仍需执行平台检查。
